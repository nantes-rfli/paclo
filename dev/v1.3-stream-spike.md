# Paclo v1.3 stream spike

Status: released / public API frozen / all gates passed

Date: 2026-08-01

## Question

Can Paclo expose a small, backend-neutral fan-out abstraction whose branches
compose with standard Clojure sequence and reduction functions while retaining
bounded memory, deterministic cancellation, and per-branch overload evidence?

## Prototype and production path

The original experiment remains outside the public API:

- `dev/paclo/dev/stream_spike.clj`
- `dev/paclo/dev/stream_spike_bench.clj`
- `test/paclo/stream_spike_test.clj`

One dispatcher consumes a generic seqable source. Every named branch owns a
bounded buffer and an opaque handle implementing:

- `clojure.lang.Seqable`
- `clojure.lang.IReduceInit`
- `java.io.Closeable`

The same contract was tested with three internal backends:

- `ArrayBlockingQueue`
- `LinkedBlockingQueue`
- core.async fixed-buffer channels

The public design remains backend-neutral.

The selected core.async design is now hardened as a production internal:

- `src/paclo/stream/impl.clj`
- `test/paclo/stream_impl_test.clj`

The namespace remains outside the public compatibility contract. It removes
the experimental backend selector while preserving opaque
`Seqable`/`IReduceInit`/`Closeable` handles.

## Correctness result

The focused suite completed with 11 tests and 171 assertions.

Covered behavior:

- nil values and source order
- seq, reduce, and transduce parity
- one handle and one consumer per branch
- `reduced` cleanup and last-branch cancellation
- consumer failure isolation
- source error propagation to stats and branch consumers
- independent branch close
- slow dropping-branch isolation
- full blocking-buffer close
- cancellation of a waiting infinite source
- idempotent close

All three backends passed the same suite. clj-kondo reported zero errors and
zero warnings for the prototype, benchmark, and tests.

The full repository suite completed with 247 tests and 846 assertions.
Eastwood reported the existing 56 warnings and no new warning in the spike
namespaces. The existing performance gate passed at 406.3 ms
(`warn=1000`, `fail=1200`).

The production-internal suite adds 14 tests and 142 assertions. It also checks
the following terminal branch invariants:

```text
offered = enqueued + dropped + cancelled
enqueued = delivered + abandoned + buffer depth
0 <= buffer depth <= capacity
0 <= maximum buffer depth <= capacity
blocking branch dropped = 0
```

It also verifies that the head of a consumed lazy source can be garbage
collected while the fan-out handle remains reachable. This regression test
guards against retaining every realized packet through the source head.
Concurrent running snapshots are EDN-readable, have monotonic counters, and
keep current and maximum depths within capacity.

The full repository suite now completes with 269 tests and 1,005 assertions.
clj-kondo reports no errors or warnings, and Eastwood reports no new warnings.

## Measurement

Command:

```bash
clojure -M:dev -m paclo.dev.stream-spike-bench \
  --count 200000 \
  --runs 3 \
  --warmups 1 \
  --output target/stream-spike-reference-v2.edn
```

Reference environment:

- macOS 15.4.1, x86_64, 12 logical processors
- Eclipse Temurin 21.0.11
- Clojure 1.12.1
- libpcap 1.10.1
- source commit `f7915b92cc37d6fc13811a98b7058c0d2c3b8ff0`

Median results:

| Scenario | Values/s | Allocated bytes/value | ns/value |
| --- | ---: | ---: | ---: |
| direct reduce control | 36,878,813 | 48.5 | 27.1 |
| JDK array, one branch | 592,119 | 343.1 | 1,688.9 |
| JDK linked, one branch | 637,007 | 363.1 | 1,569.8 |
| core.async, one branch | 1,230,305 | 621.3 | 812.8 |
| JDK array, two branches | 163,397 | 534.6 | 6,120.1 |
| JDK linked, two branches | 165,823 | 578.2 | 6,030.5 |
| core.async, two branches | 737,647 | 1,092.0 | 1,355.7 |
| JDK array, slow dropping branch | 345,929 | 479.7 | 2,890.8 |
| JDK linked, slow dropping branch | 335,616 | 502.2 | 2,979.6 |
| core.async, slow dropping branch | 881,314 | 817.3 | 1,134.7 |

Every slow-branch run delivered the complete 200,000-value sequence to the
fast branch. The intentionally unconsumed 64-entry dropping branch reported
199,936 drops.

### Production internal check

At the pre-combined implementation checkpoint, three warm-up runs and seven
measured runs of the selected production internal gave these medians:

| Scenario | Values/s | Allocated bytes/value | ns/value |
| --- | ---: | ---: | ---: |
| core.async production, two branches | 703,696 | 1,035.8 | 1,421.1 |
| core.async production, slow dropping branch | 786,469 | 763.0 | 1,271.5 |

The two-branch result is within approximately 4.6% of the Slice 0 prototype
reference and remains above the approximately 369k pps loopback floor. The
slow-dropping run again delivered all 200,000 values to the fast branch and
reported 199,936 slow-branch drops.

### Combined managed-capture check

The reproducible combined runner is:

```bash
clojure -M:dev -m paclo.dev.stream-combined-bench \
  --scenario managed-offline-dual \
  --count 500000 \
  --runs 5 \
  --warmups 3 \
  --queue-cap 4096 \
  --branch-cap 4096 \
  --output target/managed-offline-dual-final.edn
```

Five measured runs after three warm-ups gave these medians:

| Scenario | Packets/s | Allocated bytes/packet | Peak heap |
| --- | ---: | ---: | ---: |
| managed offline control | 580,086 | 636.6 | 76.0 MB |
| managed offline, two blocking branches | 471,454 | 981.2 | 207.1 MB |
| managed offline, slow dropping branch | 576,014 | 854.2 | 194.6 MB |

Both blocking branches received all 500,000 packets. The fast branch in the
dropping scenario also received all 500,000 packets while the unconsumed
64-entry branch reported 499,936 drops.

The first two-million-packet combined run under `-Xmx256m` failed with
`OutOfMemoryError`. The fan-out runtime retained the head of the managed
capture lazy sequence, which in turn retained every realized tail. The runtime
now transfers source ownership to the dispatcher and clears that root before
iteration. The final immediate-handler implementation completed the same
two-million-packet run at 509,709 packets/s and 974.4 bytes/packet with both
branches complete and a 115.1 MB heap peak.

Separate-JVM exact-count loopback probes removed the in-process sender from
the measured capture JVM:

| Scenario | Generator realized | Fast/left received | Slow/right result | Kernel/queue drop |
| --- | ---: | ---: | ---: | ---: |
| two blocking branches | 263,214 pps | 2,000,000 | 2,000,000 | 0 / 0 |
| slow dropping branch | 286,037 pps | 1,000,000 | 64 delivered, 999,936 dropped | 0 / 0 |

The local generator did not realize the historical 369k pps floor, so these
results establish a new zero-drop observation at approximately 286k pps but
do not prove the 369k acceptance criterion.

`tcpreplay` subsequently realized 399,995 pps on `lo0`, but packets injected
through its BPF handle were not visible to the independent libpcap capture
handle: the exact-count receiver observed zero packets. This is not valid
throughput evidence. Replaying on the active `en1` interface would emit the
traffic onto the real network and was intentionally not attempted.

### Linux exact-count live gate

The remaining gate was completed on 2026-08-01 on Linux x86_64 with JDK
21.0.12 and libpcap 1.10.4/TPACKET_V3. The tracked separate-JVM
`paclo.dev.perf-generator` realized approximately 400k pps with eight senders.
The receiver used a 128 MiB buffered libpcap ring; the managed-capture queue
and every fan-out branch remained bounded.

| Scenario | Generator realized | Fan-out interval | Branch result | Kernel/queue drop | Allocation |
| --- | ---: | ---: | --- | ---: | ---: |
| two blocking branches | 399,986 pps | 391,773 pkt/s | left/right 2,000,000 | 0 / 0 | 1,136.0 B/packet |
| slow dropping branch | 399,974 pps | 383,730 pkt/s | fast 1,000,000; slow 64/999,936 dropped | 0 / 0 | 926.1 B/packet |

Linux loopback counted both directions in `pcap_stats.received`, but the exact
Paclo delivery counts, libpcap drop counters, managed queue counters, and
branch counters were consistent. A 16 MiB immediate-mode TPACKET_V3 run
overloaded before this platform-specific buffered-ring tuning was applied.
The passing configuration changes no public default.

## Interpretation

The direct reducer is a control, not a release gate. Fan-out introduces an
asynchronous distribution boundary and should only be selected when at least
two consumers are required. A one-branch fan-out cannot stay within 5% of a
direct in-thread reduction and does not provide enough value to justify its
cost.

For the actual two-branch use case, core.async produced approximately 4.5
times the throughput of both JDK queue prototypes. It also allocated about
1.9 times as many bytes per value as the JDK array prototype. The throughput
result favors core.async for the next prototype stage, while the allocation
cost must remain visible in the managed-capture measurement.

The core.async two-branch and slow-dropping results exceed the existing
approximately 369k pps loopback zero-drop observation. This is encouraging,
but it is not a substitute for a combined managed-capture benchmark.

## Decision

Proceed to the next implementation slices with these constraints:

1. Keep the public API backend-neutral.
2. Use core.async as the provisional internal backend.
3. Treat two branches as the minimum meaningful public fan-out topology.
4. Keep one-branch measurements as a control, not as a 5% direct-reduce gate.
5. Add `packet-xf` before integrating decode with branch consumers.
6. Do not freeze or publish `paclo.stream` until the combined managed-capture
   loopback and allocation measurements pass.

Items 2 and 5 are implemented. Combined correctness, slow-branch isolation,
bounded heap, the 1,250 bytes/packet allocation gate, and the historical live
floor now pass. The public `paclo.stream` facade is therefore frozen with the
backend-neutral contract from this ADR.

## Release-gate result

The implementation and release-preparation PRs passed the required Linux/JDK
21, macOS ARM64/JDK 17, arm64 monitor, coverage, Eastwood, package,
performance, namespace-load, and format/lint jobs. The publish dry-run passed
on the exact release commit. Clojars publication, clean consumer resolution,
the GitHub Release, and an 11-namespace cljdoc build all completed
successfully.

The public contract distinguishes `:dropped`, `:cancelled`, and `:abandoned`,
and public `fan-out` requires at least two branches. Those decisions are now
covered by tests and the schema-version 1 statistics contract.
